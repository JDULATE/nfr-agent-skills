# Queue-screen visual example

This is a hypothetical design comparison, not an observed preference result.

## Inputs and preserved state

The screen shows synthetic jobs `job-slate` queued and `job-amber` failed.
Each row has a name, textual status, and the same permitted details action.
Candidate Original uses a dense border grid. Candidate Soft groups rows with
spacing and a quieter surface. Both keep status text and all actions.
The audience, viewport, and permitted brand changes must be supplied by the user.

| Checkpoint | Original | Soft | Carried state |
| --- | --- | --- | --- |
| Populated render | Same job names and states | Same job names and states | Task data unchanged |
| Visual prompt | Appeal question before task | Same question before task | Prompt and context retained |
| Recognition review | Status/action visible | Status/action must remain visible | No functional waiver |
| Response | Not yet collected | Not yet collected | No declared winner |

## Requirement proposal

Illustrative example; confirm with the user/stakeholder:
Use a 5-point visual-appeal scale with the anchored prompt from the skill, retain
individual response categories and reasons, and ask which decision rule to apply.
Do not fabricate favorable responses or infer a population-wide preference.

## Concrete comparison and rejection

Produce the populated renders and a ledger: border treatment, spacing, and surface
all changed together. A preference for Soft would support that bundle only.
If its failed status becomes recognizable only on hover, reject that regression
under the preservation constraint rather than calling it an aesthetic trade accepted.

A faster details click would be task evidence; it would not answer the appeal
question. A screenshot judgment would not establish sentiment after a failed job.
No actual renders, audience responses, or task observations were collected here.
