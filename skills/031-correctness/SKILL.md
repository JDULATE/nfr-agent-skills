# Correctness

## Definition and scope

Correctness means behavior matches its agreed specification for the stated inputs
and conditions. Establish expected outputs and state transitions independently
of the implementation being checked.
Separate specified behavior from external reference error (`accuracy`),
required-set omissions (`completeness`), and selected-rule checking (`conformance`).

## Use when / Don't use when

- Apply when a branch, boundary, or state transition contradicts an approved
  behavioral contract.
- Include returned values, refused operations, and required state effects.
- Route closeness to a measured reference to `accuracy`.
- Route an absent required member of a bounded universe to `completeness`.
- Route an artifact-level result against a supplied schema or convention to
  `conformance`; a functional rule may overlap, so identify the acceptance unit.

## Workflow

1. Clarify: Read source, specifications, relevant tests, domain examples, and
   callers before proposing expected behavior.
   Identify the authoritative input/output and state-transition rules.
   If sources conflict or expected behavior is missing, then Ask the user
   to resolve the contract instead of making the current implementation its oracle.

2. Specify: Record preconditions, inputs, expected outputs, state transitions,
   rejected cases, and the boundary where effects become observable.
   If the user provides no target, then propose a labeled illustrative default:
   every enumerated contract case matches its stated output and state effect;
   confirm with the user/stakeholder.
   For a practical defect, ask at most three questions covering the authoritative
   rule, relevant boundaries, and permitted side effects before implementing.
   State every assumption and proposed default to the user before building; ask at most
   three questions, and stop for the user's reply only when a decision goes beyond the
   smallest version.

3. Design/Implement: Read [behavior decisions](./references/design-guide.md)
   when fixing predicates, state guards, or result/effect ordering.
   If a boundary case violates an inclusive rule, then repair the predicate
   and exercise values on both sides as well as equality.
   If the returned result matches but state effects differ, then repair or expose
   that separate contract failure rather than accepting output-only evidence.
   Build the smallest version that meets the request; list larger extensions as offers
   and add them only with the user's yes.

4. Verify: Run the specified cases through the actual function or path, capturing
   outputs and before/after state. Retain rejected and failed cases.
   If the expected values were generated by the implementation under test, then
   replace that circular oracle with a specification-grounded expectation.

5. Report: Return the resolved contract, minimal behavior change, regression
   evidence, and cases not established by the checks.
   If only finite fixtures were run, then report those results without claiming
   a proof for every possible input or state.

## Specification patterns

- **Output:** Given `{preconditions_and_inputs}`, `{operation}` shall return
  `{specified_output}` under `{behavior_rule}`, verified by
  `{independently_derived_expected_cases}`.
- **State:** Executing `{operation}` in `{initial_state}` shall produce
  `{required_transition_and_observable_effects}`, while `{rejected_case}`
  shall preserve `{protected_state}`, checked by `{before_after_fixture}`.

Use the illustrative case-agreement proposal in Specify if no numeric objective
exists; confirm with the user/stakeholder before accepting the behavior contract.

## Rules of thumb

- Derive expected results from the chosen behavior contract, not a copy of the
  function's current branches; otherwise a wrong predicate supplies its own oracle.
- Compare state effects as well as return values when the contract names both;
  a correct response with the wrong transition still violates the specified behavior.
- Keep precondition failures distinct from valid-input results; returning a plausible
  normal value for a prohibited state can conceal the missing contract guard.

## Verification

Use specification-based examples, boundary tests, and state-transition review.
Derive expected outcomes before running the changed implementation.
Exercise accepted and refused states, equality boundaries, and repeated operations
when their contract defines them. Compare unchanged neighboring behavior.
For inclusive or exclusive bounds, test equality itself; nearby values cannot
settle the boundary predicate.
Keep original failure inputs and observable state in regression evidence.
Use generated cases only with a justified oracle or stated invariant.
Do not infer complete input coverage from branch execution counts.
Separate finite testing from a formal proof claim.

## Done checklist

- [ ] Resolve the authoritative behavioral rule and conflicting sources.
- [ ] Derive expected values independently of the implementation.
- [ ] Reproduce the reported wrong branch or transition.
- [ ] Exercise equality and adjacent contract boundaries where applicable.
- [ ] Compare required outputs and state effects together.
- [ ] Check prohibited-state refusal without forbidden mutation.
- [ ] Record neighboring regression cases and untested behavior.

## Failure modes

- Copying implementation logic into the expected-result calculation.
- Fixing nearby cases while leaving the equality boundary wrong.
- Accepting a matching output while ignoring an incorrect state effect.
- Quietly changing the specification to match the existing defect.
- Claiming finite examples establish every possible behavior.
